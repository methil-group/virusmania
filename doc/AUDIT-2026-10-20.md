Le dossier `Framework` fournit des contrôleurs singleton, une base de fenêtres et des bases de données ScriptableObject. Le joueur est composé de modules sérialisés `Updatable` pour le déplacement, l’interaction et la caméra. Les machines partagent une abstraction `Interactable`, puis `ItemHolderInteractable` pour les échanges d’objets.

La séparation entre les définitions immuables des objets (`Item`, `VirusItem`, recettes) et leurs exemplaires manipulés (`HoldItem`) est adaptée au jeu. Les événements relient les achats, la cuisson, la fusion et l’expédition au tutoriel. La progression normale sélectionne les briefs restants par difficulté et se termine après les trois commandes disponibles.

Les limites principales de cette architecture sont les dépendances implicites entre singletons, l’usage direct de données globales pour activer/désactiver les commandes, et la logique d’ouverture de fenêtres dupliquée dans plusieurs classes. Ce sont surtout ces deux derniers points qui produisent les incohérences relevées ci-dessous.

## Anomalies de code à corriger

Les scénarios ci-dessous sont établis à partir du code et de la configuration effectivement chargée. Sauf mention explicite, leur effet utilisateur n’a pas été reproduit au cours d’une partie complète. P1 désigne ici un problème à traiter avant une publication concernée ; P2, un défaut fonctionnel à planifier rapidement. Aucun P0 n’a été identifié dans le périmètre vérifié.

### 1. P1 pour le WebGL — un ancien cache peut continuer à servir une ancienne version

Le service worker appelle `caches.match(e.request)` sans limiter la recherche au cache de la version courante. Il ne contient pas non plus de traitement `activate` supprimant les caches antérieurs. Or les caches sont consultés dans l’ordre de leur création : un ancien fichier portant la même URL peut gagner sur celui qui vient d’être précaché. Ce comportement de l’API est confirmé par [la documentation MDN](https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage/match).

La configuration renforce ce scénario : cache WebGL activé, noms de fichiers sans hash, version du produit actuellement `1.0.0`. Un joueur revenant sur le même hébergement après une mise à jour risque de recevoir d’anciens fichiers, voire un mélange entre la page et les ressources du jeu.

Correction proposée : utiliser `cache.match()` sur le cache courant, supprimer les anciens caches appartenant à ce jeu lors de l’activation, puis définir une stratégie de versionnement des ressources. Vérifier deux déploiements successifs dans un navigateur ayant déjà joué.

Source : [ServiceWorker.js](C:/Users/eth/Documents/GitHub/virusmania/unity/Assets/WebGLTemplates/VirusMania/ServiceWorker.js:29).

### 2. P2 — le rebind de l’interaction ne modifie pas l’appui long

`StartRebind()` effectue le rebind uniquement sur `binding.bindings[0]`. La boucle suivante sauvegarde les autres actions, sans leur appliquer la nouvelle touche. L’inspection du prefab confirme que le groupe interaction contient `Interact` puis `LongInteract`, tous deux initialement sur E.

Après avoir remplacé E par F, la prise/dépose utilise donc F tandis que la fusion ou l’analyse par maintien reste sur E. L’interface présente pourtant un seul réglage pour cette commande.

Correction proposée : reporter le chemin de contrôle choisi sur chaque paire action/index du groupe, puis sauvegarder chaque action. Vérifier la prise, la dépose, la fusion et l’analyse après rebind et après redémarrage du jeu.

Sources : [ControlOptionsController.cs](C:/Users/eth/Documents/GitHub/virusmania/unity/Assets/Scripts/Core/MainMenu/ControlOptionsController.cs:26), [ControlOption.prefab](C:/Users/eth/Documents/GitHub/virusmania/unity/Assets/Resources/Prefabs/MainMenu/ControlOption.prefab:113).

### 3. P2 — les fenêtres n’ont pas une gestion cohérente des commandes

La bibliothèque appelle l’implémentation de base pour s’ouvrir ; celle-ci affiche le panneau mais ne désactive pas les commandes du joueur. Il est donc possible de continuer à se déplacer et à interagir derrière la liste des recettes.

L’écran d’analyse désactive bien ces commandes, mais n’est pas enregistré dans `UserInterfaceController`, qui ne connaît que l’ordinateur et la bibliothèque. Échap/Start ouvre alors la pause au lieu de fermer l’analyse. La fermeture de la pause réactive ensuite les commandes sans vérifier si l’analyse est encore ouverte. Les fenêtres de brief présentent une fragilité similaire vis-à-vis de la pause.

Correction proposée : gérer explicitement la fenêtre active et l’état de verrouillage des commandes. Fermer une fenêtre doit rétablir les commandes uniquement si aucun autre état ne les bloque. Couvrir au minimum les combinaisons bibliothèque/déplacement, analyse/pause et brief/pause.

Sources : [MergeLibraryInterface.cs](C:/Users/eth/Documents/GitHub/virusmania/unity/Assets/Scripts/Core/MergeLibrary/MergeLibraryInterface.cs:98), [UserInterfaceController.cs](C:/Users/eth/Documents/GitHub/virusmania/unity/Assets/Scripts/Core/UI/UserInterfaceController.cs:20), [PauseMenu.cs](C:/Users/eth/Documents/GitHub/virusmania/unity/Assets/Scripts/Core/Pause/PauseMenu.cs:109).

### 4. P2 — la pause peut corrompre durablement l’animation du liquide

`Wobble.Update()` divise le déplacement par `Time.deltaTime`, alors que la pause fixe `Time.timeScale` à zéro. Sur une fiole immobile, la division produit `NaN`, qui se propage dans les accumulateurs et dans les paramètres de matériau. Reprendre la partie ne réinitialise pas ces valeurs.

Le calcul a été vérifié dans Unity. Le script est attaché à neuf prefabs d’ingrédients ; le matériau inspecté utilise bien `_WobbleX`. L’étendue exacte des défauts visuels reste à constater en jeu.

Correction proposée : traiter le delta nul avant le calcul de vitesse et conserver des accumulateurs finis. Vérifier une pause avec des fioles dans la main, sur une machine et dans le chariot.

Source : [Wobble.cs](C:/Users/eth/Documents/GitHub/virusmania/unity/Assets/Scripts/Utils/Wobble.cs:45).

### 5. P2 — la musique adaptative n’est pas raccordée au timer créé dans Game

`SFXController` persiste avec `DontDestroyOnLoad`, mais ne s’abonne au timer que dans son premier `Start()`. Le parcours normal commence dans SplashScreen, qui ne contient aucun timer. Le contrôleur persiste ensuite jusque dans Game, sans nouveau `Start()` et sans abonnement au timer de cette scène.

La montée en intensité musicale prévue à 60 et 30 secondes ne dispose donc pas de son événement dans ce parcours. En démarrant directement Game dans l’Editor, l’abonnement peut fonctionner, ce qui peut masquer le problème. Autre point : `ResetMusicState()` n’a aucun appel dans le code applicatif ; les indicateurs des pistes ne sont pas réinitialisés entre briefs.

Correction proposée : raccorder/déraccorder le contrôleur au timer lors des changements de scène et réinitialiser l’état à chaque nouvelle mission. Tester le parcours depuis SplashScreen sur deux briefs successifs.

Source : [SFXController.cs](C:/Users/eth/Documents/GitHub/virusmania/unity/Assets/Scripts/Core/SFX/SFXController.cs:31).

### 6. P2 — un double clic peut invalider l’acceptation d’un brief

`PutNewBrief()` affecte le brief courant puis vide `_tempNewBrief`. Le bouton reste utilisable pendant les 0,4 seconde de fermeture animée. Un second appel affecte alors `actualBrief = null` avant de tenter de lire `_tempNewBrief.timeForBrief`, ce qui provoque une exception. Le timer du premier appel peut continuer alors que la mission courante a été effacée.

Correction proposée : rendre l’acceptation idempotente, vérifier qu’un brief est en attente et désactiver le bouton dès le premier clic. Réactiver le bouton à la préparation du brief suivant.

Source : [BriefInterface.cs](C:/Users/eth/Documents/GitHub/virusmania/unity/Assets/Scripts/Core/Brief/BriefInterface.cs:129).

### 7. P2 — l’annulation d’un rebind n’a pas de nettoyage

Le rebind désactive l’action et affiche « Press a key... ». Il autorise l’annulation par Échap, mais ne définit qu’un callback `OnComplete`. Le chemin d’annulation ne restaure donc ni l’état de l’action ni le libellé, et ne libère pas explicitement l’opération. L’opération n’est pas non plus conservée pour être annulée lorsque le panneau disparaît.

Correction proposée : partager un nettoyage entre complétion, annulation et fermeture du panneau ; restaurer l’état initial de l’action et actualiser le libellé. Tester Échap et la fermeture du panneau pendant l’attente d’une touche.

Source : [ControlOptionsController.cs](C:/Users/eth/Documents/GitHub/virusmania/unity/Assets/Scripts/Core/MainMenu/ControlOptionsController.cs:30).

## Gameplay et contenu

Le graphe de fabrication est cohérent pour le contenu actuel. Les coûts minimaux ci-dessous proviennent des prix d’achat et des recettes enregistrées, sans erreur du joueur, sans déplacement et sans valoriser le temps passé aux machines.

| Brief | Produit | Coût minimal | Récompense | Temps |
| --- | --- | ---: | ---: | ---: |
| Gut & Neuro | Poliovirus | 8 $ | 35 $ | 120 s |
| Latency Threat | Herpes | 28 $ | 50 $ | 120 s |
| Mutate & Bones | Influenza A | 15 $ | 80 $ | 120 s |
| Brief marqué tutoriel dans la base | Parvovirus B19 | 8 $ | 15 $ | 120 s |

La scène Game commence effectivement avec **20 $**, malgré la valeur par défaut de 15 dans la classe C#. La première commande est donc finançable ; les récompenses permettent de financer les suivantes. Aucun produit demandé inaccessible n’a été détecté.

Le tutoriel comporte cinq étapes. Ses achats sont limités à un exemplaire par ingrédient, puis masqués après l’achat. Cela guide correctement le parcours prévu, mais ne prévoit pas de récupération si le joueur détruit un ingrédient ou le produit demandé dans la poubelle. Il faut alors quitter et recommencer le tutoriel. Ajouter un réapprovisionnement contrôlé ou une reprise d’étape améliorerait la tolérance aux erreurs.

Le contenu est encore court et peu variable : trois briefs de partie normale, même durée pour chacun, aucun brief de difficulté Hard dans les données présentes. Pour prolonger le jeu, les prochaines données devraient modifier les contraintes ou les recettes requises, avec un équilibrage du temps de parcours réel. Ajouter des classes n’est pas nécessaire pour simplement augmenter le nombre de commandes.

## Performance, assets et rendu

Les fichiers sources suivis sous `unity/Assets`, hors `.meta`, représentent environ **255,2 Mio**, dont **248,0 Mio** dans `Resources`. Il s’agit de tailles sources : elles ne mesurent ni le téléchargement compressé final ni la mémoire consommée en jeu.

Le dossier `Resources/Models/Test` contient deux fichiers Alembic strictement identiques de **32,7 Mio chacun**, égalité vérifiée par SHA-256. Ces assets de test et leur doublon sont une cible évidente de nettoyage. Unity inclut les assets des dossiers Resources dans le Player même sans référence directe depuis une scène ; c’est confirmé dans [sa documentation du contenu d’un build](https://docs.unity.com/en-us/engine/6000.5/manual/building-and-publishing/build-content-output). Le gain exact après nettoyage doit être mesuré sur un build.

Autres points à optimiser après mesure :

- `PlayerInteraction` alloue un tableau via `Physics.OverlapSphere` et un nouveau `HashSet` à chaque frame ; le maintien d’interaction ajoute une autre recherche physique. Réutiliser les buffers limiterait les allocations.
- La sélection prend le premier collider éligible sans filtre de couche ni choix explicite de la cible la plus proche. Cela rend les zones qui se chevauchent plus difficiles à régler.
- `InInteractZone()` relance chaque frame les événements et certains tweens d’indicateur. Distinguer l’entrée dans la zone de la présence continue éviterait de redémarrer constamment les animations.
- Plusieurs composants créent des matériaux avec `new Material` sans destruction explicite. `Wobble` est particulièrement concerné puisque les fioles sont instanciées/détruites lors des échanges. Mesurer la croissance des matériaux après des manipulations répétées, puis gérer leur durée de vie ou employer un `MaterialPropertyBlock` pour les paramètres adaptés.
- La cible de fréquence configurée est 120 FPS, avec VSync désactivée par `FPSLimiter`. Pour un petit jeu de laboratoire, évaluer le rapport fluidité/coût sur des machines modestes avant de conserver ce choix.

Les shaders personnalisés et le post-traitement donnent une identité visuelle au projet. L’inspection sans affichage ne permet toutefois pas d’attester leur rendu WebGL, leur coût GPU, les masques UI ou la lisibilité à diverses résolutions.

## Builds, dépendances et maintenance

Le script WebGL fixe les quatre scènes et vérifie bien le résultat de `BuildPipeline.BuildPlayer`, ce qui évite de traiter un build échoué comme une réussite. Le serveur Nginx prévoit les types MIME et les en-têtes pour Brotli.

Trois limites restent à traiter :

1. **Versions Unity divergentes.** Docker utilise `6000.2.2f1`, le dépôt `6000.6.0f1` et la copie de travail `6000.6.6f1`. La réussite de la compilation locale n’établit pas la compatibilité de l’image Docker avec les packages actuels. Choisir une version de référence, puis aligner le projet, l’image et les builds automatisés.
2. **CI déclenchée uniquement sur tags `v*`.** Le workflow distribue quatre cibles desktop mais ne valide pas les pull requests, ne lance pas de tests et ne construit pas WebGL. Ajouter une compilation de validation sur PR, puis quelques tests des règles de recettes, du timer et des états d’interface. Garder le travail de release séparé.
3. **Reproductibilité et poids du contexte Docker.** L’image Nginx est flottante et aucun `.dockerignore` n’est suivi. Un build depuis un répertoire de travail peut transférer `Library`, les logs et d’autres fichiers générés via `COPY . .`. Le manifeste du toon shader vise aussi une branche Git sans tag explicite, même si le lockfile conserve actuellement une révision précise. Encadrer les mises à jour et limiter le contexte envoyé au build.

Pour Git et la documentation : le fichier racine s’appelle `.gitingore`, donc ses règles ne s’appliquent pas. Le projet Unity dispose bien de son propre `.gitignore`, mais des `.DS_Store`, sauvegardes Blender et une scène de récupération sont déjà suivis. Le nom erroné devrait être corrigé et les fichiers inutiles retirés explicitement de l’index ; une règle d’ignore ne retire pas un fichier déjà versionné.

Le README décrit bien le jeu, ses commandes et les crédits. Il manque un guide développeur : version Unity de référence, ouverture du dossier `unity/`, scène de démarrage, construction desktop/WebGL, variables CI nécessaires et procédure de vérification avant release. La documentation AsciiDoc contient encore des éléments de conception qui divergent du jeu actuel. Aucune licence générale du projet n’a été identifiée à la racine ; des notices existent pour certains composants tiers.
